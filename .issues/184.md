# `perf:` `fix_context` causes OOM on large streaming batches by materializing full `__base` CTE unnecessarily

## Summary

`Processor.fix_context` (`fabricks/cdc/base/processor.py`) renders the full `filter.sql.jinja` template (including `ctes/base.sql.jinja`) to determine a simple timestamp slice boundary. The `__base` CTE computes `md5()` hashes for ALL columns on ALL source rows, even though `fix_context` only needs `MAX(__timestamp)` per `__source` from the **target** table. For large streaming batches, the in-memory expansion causes `OutOfMemoryError`.

## Environment

- fabricks: 4.0.22
- Databricks Runtime: 17.3
- Multi-node production cluster (scheduled pipeline run), Standard_D4ds_v5 nodes (16 GB RAM, 4 vCores each)
- Table config: silver streaming SCD1, multiple parents, `deduplicate: true`

## Root Cause

Call chain:

```
silver.for_each_batch
  -> cdc.update(sql, **context)               # scd.py:21 injects mode="update"
    -> merge(src, **kwargs)                    # merger.py:110
      -> get_data(src, **kwargs)               # processor.py:25
        -> get_query(src, fix=True, **kwargs)  # processor.py:433
          -> get_query_context(...)            # sets slice="update" (line 134-136)
            -> fix_context(context, ...)       # processor.py:438-439
```

`fix_context` (line 408-431) runs on the **driver** — it is a Python function called inside the `for_each_batch` callback. It renders `filter.sql.jinja` and then calls `self.spark.sql(sql).collect()[0]` to retrieve the result. The SQL itself is dispatched to the cluster and executes on executor nodes:

1. `ctes/base.sql.jinja` builds `__base` with an `md5()` hash of all fields for every row in the batch — this is the expensive part, running fully on executors
2. `filters/update.sql.jinja` only needs the distinct `__source` values and `MAX(__timestamp)` from the target table

The entire `__base` CTE is wasted work in this context.

### Why it OOMs

Parquet's columnar compression can achieve extreme ratios (50-100x) on wide tables with repeated strings and low-cardinality columns. A seemingly small on-disk batch (e.g. 200 MB) can expand to 15-20 GB in Spark's in-memory row format when all columns are materialized with hash computations. On Standard_D4ds_v5 executors (16 GB RAM each), a single large partition can exhaust an executor's heap before it can spill to disk.

Spark then tries to join the fully materialized batch against the target table using a **Sort-Merge Join**: both sides are sorted on the join key and merged row by row. This requires buffering large amounts of data in memory simultaneously. The Sort-Merge Join codegen runs on executor nodes, so the heap exhaustion is expected to surface there (the driver only receives a single aggregated row via `.collect()` and is not the bottleneck):

```
java.lang.OutOfMemoryError: Java heap space
  at ExternalAppendOnlyUnsafeRowArray.add(ExternalAppendOnlyUnsafeRowArray.scala:177)
  at GeneratedIteratorForCodegenStage4.smj_findNextJoinRows_0$
  at GeneratedIteratorForCodegenStage4.hashAgg_doAggregateWithKeys_0$
```

### Why batches accumulate

`write_stream` uses `trigger(once=True)`, meaning ALL data since the last checkpoint is processed in a single micro-batch. When bronze receives periodic full-load appends and the stream fails, subsequent runs accumulate more data, making the problem worse on each retry. The stream cannot self-recover.

## Reproduction

1. Configure a silver streaming SCD1 table with `stream: true` and multiple parents
2. Append several full loads to one bronze parent (each a few million rows, wide schema)
3. Run the pipeline on a multi-node cluster with Standard_D4ds_v5 executors (16 GB RAM each)
4. The stream accumulates all unprocessed loads into one batch
5. `fix_context` submits a SQL query that materializes the entire batch with hash computations on the executors -> OOM

## Proposed Fix

Replace the template-based approach in `fix_context` with a direct query that only touches what's needed. The fix must handle both `slice == "update"` (query target for `max(__timestamp)`, filter with `>`) and `slice == "latest"` (query source for `max(__timestamp)`, filter with `==`). Note that for "latest" mode, `tgt` is `None` since there is no target table.

```python
# chr(39) produces a single-quote character at runtime. Neither '' (sqlglot
# treats as adjacent empty strings) nor \' (escapedStringLiterals removed in
# DBR 17.3) work for quoting inside generated SQL filter fragments.
_Q = "chr(39)"

def fix_context(self, context, fix=False, **kwargs):
    tgt = context.get("tgt")
    has_source = context.get("has_source")
    src = context.get("src")
    src_format = context.get("format")
    slice_type = context.get("slice")

    src_ref = f"({src})" if src_format == "query" else str(src)

    if slice_type == "latest":
        # "latest" mode: get max timestamp from SOURCE, filter with ==
        if has_source:
            sql = f"""
                SELECT
                    array_join(collect_list(slices), ' or ') AS slices,
                    array_join(collect_list(sources), ' or ') AS sources
                FROM (
                    SELECT
                        concat('t.__source == ', {_Q}, __source, {_Q}) AS sources,
                        concat_ws(' ', ' (',
                            concat('s.__timestamp == ', {_Q}, max(__timestamp), {_Q}),
                            concat('and s.__source == ', {_Q}, __source, {_Q}),
                            ' )') AS slices
                    FROM {src_ref}
                    GROUP BY __source
                )
            """
        else:
            sql = f"""
                SELECT concat_ws(' ', ' (',
                    concat('s.__timestamp == ', {_Q}, max(__timestamp), {_Q}),
                    ' )') AS slices
                FROM {src_ref}
            """
    elif has_source:
        # "update" mode with __source: get max timestamp from TARGET per source
        sql = f"""
            WITH __sources AS (
                SELECT DISTINCT __source FROM {src_ref}
            )
            SELECT
                array_join(collect_list(slices), ' or ') AS slices,
                array_join(collect_list(sources), ' or ') AS sources
            FROM (
                SELECT
                    concat('t.__source == ', {_Q}, s.__source, {_Q}) AS sources,
                    concat_ws(' ', ' (',
                        concat('s.__timestamp > ', {_Q},
                            coalesce(max(t.__timestamp), cast('0001-01-01' AS timestamp)), {_Q}),
                        concat('and s.__source == ', {_Q}, s.__source, {_Q}),
                        ' )') AS slices
                FROM {tgt} t
                RIGHT JOIN __sources s ON s.__source = t.__source
                GROUP BY s.__source
            )
        """
    else:
        # "update" mode without __source: get max timestamp from TARGET
        sql = f"""
            SELECT concat_ws(' ', ' (',
                concat('s.__timestamp > ', {_Q},
                    coalesce(max(__timestamp), cast('0001-01-01' AS timestamp)), {_Q}),
                ' )') AS slices
            FROM {tgt}
        """

    if fix:
        sql = self.fix_sql(sql)

    row = self.spark.sql(sql).collect()[0]
    assert row.slices, "no slices found"

    context["slices"] = row.slices
    if has_source:
        assert row.sources, "no sources found"
        context["sources"] = row.sources

    return context
```

### Performance comparison

The key insight is that `fix_context` only needs to know the distinct source identifiers (e.g. `bronze.topic_a`, `bronze.topic_b`). A silver item typically has at most 2-4 parent bronze tables, so `__sources` contains at most a handful of rows regardless of batch size.

| Metric | Before (template) | After (direct query) |
| --- | --- | --- |
| Rows read from the batch | All rows (potentially millions) | One row per distinct `__source` value (typically 1-4) |
| Hash computations | md5() over all rows x all columns | None |
| In-memory expansion | Up to tens of GB per executor | Negligible |
| Join strategy | Sort-Merge Join: both sides sorted and buffered in memory | Broadcast Hash Join: the tiny `__sources` table is broadcast to all executors; no sorting or buffering needed |
| Risk of OOM | High (16 GB executors exhausted by a single large partition) | None |

With only a few source rows, Spark automatically switches from a Sort-Merge Join (which requires sorting and buffering the full batch) to a Broadcast Hash Join (which sends just those few rows to every executor as a lookup table). This eliminates the memory pressure entirely.

## Secondary Recommendation

Consider also changing `write_stream` from `trigger(once=True)` to `trigger(availableNow=True)` with a configurable `maxBytesPerTrigger` option on the readStream. This would split large accumulated batches into multiple micro-batches as defense-in-depth, independent of the `fix_context` fix.

## Current Workaround

Monkey-patching `Processor.fix_context` at runtime in `notebooks/pipeline_utils/run` with the implementation above. Verified on the production cluster (DBR 17.3, sqlglot 30.11.0, 2026-06-16).
