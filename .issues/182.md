# `bug:` Empty slice condition generates invalid SQL in silver NoCDC `stream: false, mode: latest`

## Summary

When a silver table configured with `mode: latest` and `stream: false` produces an empty slice list, fabricks generates invalid SQL:

```sql
WHERE TRUE AND ( (  ) )
```

This causes `PARSE_SYNTAX_ERROR: Syntax error at or near ')'` (SQLSTATE: 42601) and the job fails. This is a **recurring operations bug** that surfaces in at least two scenarios: on the very first run of a newly deployed table, and on any subsequent scheduled run where no new bronze files have arrived since the last successful run.

## Environment

- Library: `fabricks` v4.0.22
- Runtime: Databricks 17.3 / Python 3.12
- Silver config: `mode: latest, stream: false, change_data_capture: nocdc`

## Root Cause

`fix_context()` in `cdc/base/processor.py` runs `filter.sql.jinja` to compute an incremental slice condition, then stores it in the context:

```python
row = self.spark.sql(sql).collect()[0]
assert row.slices, "no slices found"
context["slices"] = row.slices
```

When the slice query returns no new file paths (either because the silver target is empty on first run, or because no new bronze files have arrived since the last run), `filter.sql.jinja` returns `' (  )'` (whitespace-padded empty parentheses) as `row.slices`. This passes `assert row.slices` because `' (  )'` is truthy in Python. The value is then injected into `cdc/templates/ctes/slice.sql.jinja`:

```sql
__sliced AS (SELECT * FROM {{ parent_slice }} s WHERE TRUE AND ({{ slices }})),
```

Rendered output:

```sql
__sliced AS (SELECT * FROM __base s WHERE TRUE AND ( (  ) )),
```

The double-nested empty parens are invalid SQL. Databricks raises `PARSE_SYNTAX_ERROR` at the inner `)`.

**Affected files:**
- [`fabricks/cdc/base/processor.py`](https://github.com/fabricks-framework/fabricks/blob/main/fabricks/cdc/base/processor.py) -- `assert row.slices` + `context["slices"] = row.slices`
- [`fabricks/cdc/templates/ctes/slice.sql.jinja`](https://github.com/fabricks-framework/fabricks/blob/main/fabricks/cdc/templates/ctes/slice.sql.jinja) -- `WHERE TRUE AND ({{ slices }})`

## Observed Impact

Any silver job with `stream: false, mode: latest` that produces an empty slice fails immediately. Confirmed triggers:

- First pipeline run after initial deployment of a new silver table of this type.
- First pipeline run after a `j.drop()` + `j.create()` cycle resets the table.
- **Any scheduled run where no new bronze files have arrived since the last successful run.** This is the most common production trigger: legacy or infrequently updated sources (e.g. weekly Excel uploads) will reliably fail on every pipeline run that falls between source updates.

In our environment this has blocked 4 tables (`silver.legacy_sales_induscabel`, `silver.legacy_sales_lambrechts`, `silver.legacy_sales_sax`, `silver.legacy_sales_schrauwen`, ~23M total rows) from completing on any pipeline run where no new legacy sales file was uploaded that day.

## Proposed Fix

**Option A (recommended): guard in `fix_context()`**

After computing `row.slices`, check whether the result is an empty-paren string. If so, disable the slice CTE and fall back to processing all rows (correct behaviour -- if no new files, the full table is already up to date and the job can complete as a no-op):

```python
import re

row = self.spark.sql(sql).collect()[0]
assert row.slices, "no slices found"

slices = row.slices
if isinstance(slices, str) and re.match(r"^\(\s*\)$", slices.strip()):
    # Empty slice: no new files since last run. Skip slice CTE entirely.
    context["slice"] = None
    context["parent_slice"] = None
    if context.get("parent_deduplicate_key") == "__sliced":
        context["parent_deduplicate_key"] = "__base"
    return context

context["slices"] = slices
```

**Option B: fix `filter.sql.jinja`**

Return `NULL` or an empty string when no slices exist, so `assert row.slices` raises `AssertionError: no slices found`. Then add an explicit fallback in `fix_context()` that sets `context["slice"] = None` when the assertion fails.

## Current Workarounds

**Workaround 1 (one-time manual fix):** Monkey-patch `Processor.fix_context` before calling `j.run(reload=True)`. Note that `reload=True` is also required: without it, the incremental checkpoint reports no new batches and the run silently writes zero rows.

```python
import re
from fabricks.cdc.base.processor import Processor as CDCProcessor

_orig = CDCProcessor.fix_context

def _safe_fix_context(self, context, fix=True, **kwargs):
    result = _orig(self, context, fix=fix, **kwargs)
    slices_val = result.get("slices", "")
    stripped = slices_val.strip() if isinstance(slices_val, str) else ""
    if re.match(r"^\(\s*\)$", stripped):
        result["parent_slice"] = None
        result["slice"] = None
        if result.get("parent_deduplicate_key") == "__sliced":
            result["parent_deduplicate_key"] = "__base"
    return result

CDCProcessor.fix_context = _safe_fix_context
try:
    j.run(reload=True)
finally:
    CDCProcessor.fix_context = _orig
```

**Workaround 2 (persistent, per-item):** Add `check_options: { skip: true }` to the silver YAML config entry and create a `<topic>/<item>.skip.sql` file that returns `__skip = true` when no new bronze rows exist. This prevents fabricks from reaching the slice SQL generation entirely:

```sql
SELECT
    CASE WHEN COUNT(*) = 0 THEN TRUE ELSE FALSE END AS __skip,
    'No new bronze rows since last silver run' AS __message
FROM bronze.legacy_<item>
WHERE __timestamp > (
    SELECT COALESCE(MAX(__timestamp), CAST('1970-01-01' AS TIMESTAMP))
    FROM silver.legacy_<item>
)
```

This is the workaround currently applied in our project (marked as TODO to remove on upstream fix).
