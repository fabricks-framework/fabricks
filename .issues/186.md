# `bug:` Target-table scan in `fix_context` causes job failures on large tables; replace with metadata-stored watermark

## Summary

Batch mode (`stream: false`) is the natural choice for scheduled silver jobs: run periodically, process what's new, stop. However, the current incremental mechanism (`fix_context`) derives "what's new" by scanning the **entire target table** to compute `MAX(__timestamp)` per `__source`. On tables with hundreds of millions of rows, this scan causes executor OOM and heartbeat timeouts, making the job **fail entirely**, not just run slowly. Even after the fix proposed in #184 (which eliminates unnecessary md5 hash computation), the full target scan remains and will still fail on sufficiently large tables.

This issue proposes storing a watermark (last-processed timestamp per source) in a metadata table, reducing the incremental filter derivation from O(n) to O(1). This eliminates the failure mode and makes `stream: false` the efficient and correct default for scheduled batch workloads.

**Distinction from #184**: issue #184 fixes HOW the target is queried (removing expensive hash computation). This issue proposes not querying the target at all (using a pre-stored watermark instead). They are complementary: #184 is needed as the fallback when no watermark exists yet, while this issue eliminates the target scan entirely for steady-state runs.

## Observed impact

On a production silver table (~170M rows, wide schema, SCD1 merge with multiple parents), the `fix_context` target scan consistently causes:

- **Executor heartbeat timeouts** (130s+) as executors OOM during the scan
- **Complete job failure** after retries are exhausted
- **Repeated failures across runs**: since each run re-scans the same growing target, the problem never self-resolves and worsens over time as the target grows

The job has never successfully completed without a monkey-patch that bypasses the standard `fix_context` logic. This is not a performance degradation; it is a hard blocker for large tables in batch mode.

## Motivation: why `stream: false` should be the default

Most silver jobs are not streaming workloads. They run periodically (hourly/daily), process whatever is new, and stop. Using `stream: true` for these introduces:

1. **Spark Connect process isolation**: `foreachBatch` runs in a separate worker process. Runtime patches, custom logging, and monkey-fixes applied on the driver do not propagate. This limits operational flexibility.
2. **Cascade failures**: `trigger(once=True)` processes ALL accumulated data in a single micro-batch. If processing fails due to resource constraints, the next retry has strictly MORE data, making recovery impossible without manual intervention.
3. **Checkpoint complexity**: streaming checkpoints are opaque binary state. Debugging, resetting, or advancing them requires low-level Delta log manipulation.
4. **Semantic mismatch**: streaming implies continuous processing. These jobs are batch: run, process, stop.

`stream: false` with an efficient incremental mechanism avoids all of these. The missing piece is making that mechanism cheap (and functional on large tables).

## Current behavior (`stream: false`, `mode: update`)

When `fix_context` is triggered (conditions: `mode="update"`, target has rows, `has_timestamp` is true):

1. Queries the target table for `MAX(__timestamp)` per `__source` (after #184 fix)
2. Returns a filter like `s.__timestamp > '<max_ts>' AND s.__source = '<src>'`

This scans the full target table. For tables with hundreds of millions of rows, this scan puts enough memory pressure on executors to cause OOM and heartbeat timeouts, failing the job entirely, even when only a handful of new rows need processing.

## Proposed improvement: watermark in metadata

### Concept

After a successful batch run, store the processed watermark (max `__timestamp` per `__source`) in a metadata table. On the next run, read this watermark with a simple point lookup instead of scanning the target.

### Suggested schema addition

```sql
-- New metadata table or extension to silver_jobs
CREATE TABLE IF NOT EXISTS fabricks.silver_watermarks (
    step STRING,           -- e.g. "silver"
    topic STRING,          -- e.g. "scale"
    item STRING,           -- e.g. "transaction_history"
    source STRING,         -- e.g. "bronze.scale_transaction_history"
    last_timestamp TIMESTAMP,
    last_updated TIMESTAMP,
    last_batch_id BIGINT
);
```

### Updated `fix_context` flow

```python
def fix_context(self, context, fix=False, **kwargs):
    if not fix:
        return context

    # O(1) metadata lookup instead of O(n) target scan
    watermarks = self.get_watermarks()  # reads from silver_watermarks

    if not watermarks:
        # First run or pre-upgrade: fall back to target scan (#184 path)
        return self._fix_context_from_target(context, **kwargs)

    filters = []
    for source, last_ts in watermarks.items():
        filters.append(
            f"(s.__source = '{source}' AND s.__timestamp > '{last_ts}')"
        )

    context["slices"] = " OR ".join(filters)
    return context
```

After a successful merge:
```python
def update_watermarks(self, batch_max_timestamps):
    """Called after successful batch completion."""
    # Upsert watermarks into metadata table
    for source, max_ts in batch_max_timestamps.items():
        self.spark.sql(f"""
            MERGE INTO fabricks.silver_watermarks t
            USING (SELECT '{source}' AS source, '{max_ts}' AS last_timestamp) s
            ON t.step = '{self.step}' AND t.topic = '{self.topic}'
               AND t.item = '{self.item}' AND t.source = s.source
            WHEN MATCHED THEN UPDATE SET last_timestamp = s.last_timestamp, last_updated = current_timestamp()
            WHEN NOT MATCHED THEN INSERT *
        """)
```

### Safety: idempotent by design

SCD1 merges are idempotent (upserting the same row twice produces the same result). If the merge succeeds but the watermark update fails, the next run reprocesses some data with no correctness impact. This gives the same guarantee as streaming checkpoints but with simpler state management.

### Failure recovery

If a run fails mid-merge:
- The watermark is NOT advanced (it updates only after success)
- The next run retries from the same watermark
- No data is lost, no manual checkpoint reset needed

## Performance comparison

| Metric | Current (target scan) | Proposed (watermark lookup) |
| --- | --- | --- |
| I/O to determine slice | Full scan of target (millions of rows) | Point read from metadata table (1-4 rows) |
| Time complexity | O(n) where n = target rows | O(1) |
| Memory pressure | Loads target partitions into executor memory | Negligible |
| Scales with target growth | Degrades linearly (eventually fails) | Constant |
| Failure mode | OOM / executor heartbeat timeout on large tables | Cannot fail on size |

## Impact on configuration guidance

With this change, the recommendation becomes clear:

- **`stream: false`** (batch mode): the default for all scheduled silver jobs. Efficient, debuggable, no streaming complexity.
- **`stream: true`**: reserved for genuinely streaming use cases (real-time CDC feeds, sub-minute latency requirements).

This aligns the framework's behavior with users' mental model: a scheduled batch job should use batch mode.

## Current Workaround

Monkey-patching `Processor.fix_context` and `Silver.for_each_batch` at runtime in `notebooks/pipeline_utils/run` with the full watermark approach described above:

- `fix_context` reads from a `fabricks.silver_watermarks` Delta table first (O(1)), falls back to the #184-style target query (O(n), no md5) if no watermark exists
- `Silver.for_each_batch` is wrapped to update watermarks after each successful merge
- Watermark table is created lazily, all operations are non-fatal (try/except falls back to target scan)

Only effective for `stream: false` (patches run in the driver process, do not propagate to Spark Connect foreachBatch workers). This is the workaround currently applied in our project (marked as TODO to remove on upstream fix).

## Backwards compatibility

This proposal is fully backwards compatible by design. No existing deployment will break, no migration is required, and no config change is needed to keep current behavior.

### How it stays backwards compatible

1. **Graceful fallback when no watermark exists**: if no watermark row exists for a given job (first run, or a deployment that hasn't upgraded yet), `fix_context` falls back to the current behavior (querying the target table directly, with the #184 optimization applied). Existing deployments continue working unchanged from day one.
2. **Lazy table creation**: the `silver_watermarks` table is created on first successful write. If the table does not exist, `fix_context` falls back silently. No DDL migration step required.
3. **Zero config**: the watermark mechanism activates automatically when the metadata table exists. No new YAML keys needed. Optionally, a `watermark: false` override could disable it for specific jobs, but the default behavior (with fallback) requires zero config.
4. **Gradual self-adoption**: existing deployments upgrade fabricks, runs succeed as before (fallback path). On first successful run with the new version, the watermark is written. From the second run onward, the O(1) path is used. No manual intervention.
5. **Safe rollback**: if a user downgrades fabricks to a version without watermark support, the watermark table is simply ignored. The old `fix_context` (target scan) runs as it always did. No orphaned state, no errors.

### Fallback chain

```
fix_context called
  → watermark table exists?
    → YES: watermark row for this job+source exists?
      → YES: use watermark (O(1) path) ✓
      → NO: fall back to target scan (first run for this source)
    → NO: fall back to target scan (pre-upgrade or table not yet created)
```

### Bootstrapping (optional, not required)

For users who want immediate O(1) performance without waiting for a successful run, a one-time bootstrap can populate watermarks from existing targets:

```sql
INSERT INTO fabricks.silver_watermarks
SELECT step, topic, item, __source AS source, MAX(__timestamp) AS last_timestamp, current_timestamp() AS last_updated, NULL AS last_batch_id
FROM <target_table>
GROUP BY step, topic, item, __source
```

This is entirely optional. Without it, the first run uses the fallback (target scan), writes the watermark, and all subsequent runs use the fast path.

### What does NOT change

- `mode: latest` slice logic (unchanged, does not use watermarks)
- `mode: combine` without `fix_context` (unchanged)
- Any job with `stream: true` (streaming uses checkpoints, not watermarks)
- The MERGE logic itself (only the filter derivation changes)
- The `silver_jobs` metadata table structure (watermarks go in a NEW table, not retrofitted into existing schema)
