# `bug:` `_invoke_job` wraps typed exceptions in bare `Exception`, causing unintended table RESTORE on post-run invoker failures

---

## Summary

When a post-run invoker notebook fails, the table data (successfully written in the preceding step) is rolled back via `self.restore()`. This happens because `Invoker._invoke_job()` wraps `PostRunInvokeException` objects inside a bare `Exception(errors)`, which bypasses the specific exception handler in `Processor.run()` that was designed to NOT restore on invoker failures.

This causes silent data loss on any gold table with a configured post-run invoker that fails, even though the core data write succeeded.

## Environment

- fabricks version: 4.0.23
- Runtime: DBR 17.3, Photon, single-node Standard_E8_v3
- Affected path: any job with `invoker.post_run` configured

## Root Cause

### The intended design

In [`processor.py`](https://github.com/fabricks-framework/fabricks/blob/main/framework/fabricks/core/jobs/base/processor.py), `Processor.run()` has a carefully layered exception hierarchy:

```python
# Line ~219: Invoker failures should NOT restore (data write was successful)
except (PreRunInvokeException, PostRunInvokeException) as e:
    DEFAULT_LOGGER.exception("fail to run invoker", extra={"label": self})
    raise e  # No restore!

# Line ~233: Generic failures DO restore (data write may be corrupt)
except Exception as e:
    if not self.stream or not retry:
        self.restore(last_version, last_batch)
        raise e
```

The intent is clear: invoker failures are non-critical (the data is already written), so they should propagate as errors without rolling back the table.

### The bug

In [`invoker.py`](https://github.com/fabricks-framework/fabricks/blob/main/framework/fabricks/core/jobs/base/invoker.py), `_invoke_job()` (and `_invoke_step()`) collect typed exceptions into a list, then wrap them in a bare `Exception`:

```python
# Line ~80-88 in _invoke_job():
except Exception as e:
    if position == "post_run":
        errors.append(PostRunInvokeException(e))
    else:
        errors.append(e)

if errors:
    raise Exception(errors)  # <-- bare Exception wrapping the typed exceptions!
```

The bare `raise Exception(errors)` is NOT matched by `except PostRunInvokeException` in the processor. It falls through to `except Exception`, which calls `self.restore()`.

### The same bug exists in `_invoke_step()`

The identical pattern appears in `_invoke_step()` around line ~100, with the same `raise Exception(errors)` wrapping.

## Observed Impact

- Multiple gold tables with post-run invokers are systematically RESTORE'd to their pre-run state (often empty) after every successful write
- The pattern manifests as: CREATE TABLE -> WRITE (millions of rows) -> RESTORE (back to 0 rows)
- Downstream tables that read from the affected tables inherit the data loss, cascading through the entire dependency chain
- In a production environment, this silently broke ~10 gold tables over several days before being caught

## Proposed Fix

Raise the typed exception directly instead of wrapping in a bare `Exception`. The simplest fix:

```python
# In _invoke_job() and _invoke_step(), replace:
if errors:
    raise Exception(errors)

# With:
if errors:
    if position == "pre_run":
        raise PreRunInvokeException(errors)
    elif position == "post_run":
        raise PostRunInvokeException(errors)
    else:
        raise Exception(errors)
```

Alternatively, since `invokers` is iterated and errors are collected, raising the first typed error directly would also work:

```python
if errors:
    raise errors[0]
```

Both approaches ensure the `except (PreRunInvokeException, PostRunInvokeException)` handler in `processor.py` catches the error correctly, preventing the RESTORE.

## Current Workaround

Run jobs with `invoke=False` to skip the post-run invoker entirely:

```python
j.run(invoke=False)
```

This preserves the data but skips any downstream triggering that the post-run invoker was supposed to handle.
