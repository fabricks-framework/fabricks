# `bug:` DagTerminator falsely reports pipeline failure when transient pre-run invoker errors recover on retry

## Summary

When a bronze pre-run invoker notebook fails with a transient error (e.g. `Py4JJavaError` from a JDBC connection timeout), the item is logged as `failed`. The item is subsequently re-dispatched and succeeds on retry: data is written to Delta and the extraction completes normally. However, the successful retry's lifecycle (`start` -> `running` -> `done` -> `end`) is never captured in `fabricks.logs`. The `DagTerminator.terminate()` then checks `not array_contains(collect_list(status), 'done')` and reports the item as a failure, causing the entire pipeline run to fail with `ValueError("N job(s) failed")`.

This produces **false pipeline failures** on every run that encounters a transient pre-run error, even though all data was successfully extracted.

## Environment

- **fabricks**: 4.0.23
- **Databricks Runtime**: 17.3 (Photon, USER_ISOLATION)
- **Cluster**: sinlge-node
- **Bronze config**: `mode: register`, `parser: delta`, with `pre_run` invoker notebooks (JDBC extraction via `dbutils.notebook.run()`)

## Root Cause

Three components interact to produce the false failure:

### 1. No retry at the invoker or DagProcessor level

[`invoker.py:_invoke_job()`](https://github.com/fabricks-framework/fabricks/blob/main/framework/fabricks/core/jobs/base/invoker.py#L88) calls `dbutils.notebook.run()` once. If the notebook fails (e.g. JVM-level `Py4JJavaError` on a transient network error), the exception is wrapped in `PreRunInvokeException` and raised immediately. There is no retry.

The pre-run notebook may have its own internal `@retry` decorator for JDBC calls, but a JVM-level failure at the `dbutils.notebook.run()` invocation layer bypasses that entirely.

### 2. DagProcessor.receive() unconditionally marks items as "ok"

[`processor.py:receive()`](https://github.com/fabricks-framework/fabricks/blob/main/framework/fabricks/core/dags/processor.py#L104-L155) has this structure:

```python
try:
    dbutils.notebook.run(path=..., ...)
except Exception:
    LOGGER.warning("fail", ...)
finally:
    j["Status"] = "ok"          # <-- always "ok", even on failure
    azure_table.upsert(j)
    ...

# dependencies cleared unconditionally
dependencies = azure_table.query(...)
azure_table.delete(dependencies)
```

Failed items get `Status = "ok"` and their dependencies are cleared. The `send()` thread (which polls for `Status = 'scheduled'`) never re-dispatches them. There is no retry mechanism at the DAG level.

### 3. DagTerminator checks for presence of 'done', not absence of unrecovered 'failed'

[`terminator.py:terminate()`](https://github.com/fabricks-framework/fabricks/blob/main/framework/fabricks/core/dags/terminator.py#L15-L46) evaluates:

```python
not array_contains(collect_list(status), 'done') as not_done
```

Any job missing a `done` status is reported as failed, regardless of whether:
- The item was retried and data was successfully written
- The failure was transient and self-recovered
- The item's Delta table received a write after the failure timestamp

## Observed Impact

- Pipeline runs with transient bronze JDBC errors are marked as `RUN_EXECUTION_ERROR` even though all data was extracted
- The `terminate` Databricks task fails, blocking downstream repair runs
- Recurring transient errors (network blips, connection pool exhaustion) cause nightly false failures over consecutive days
- Operators must manually verify whether failures are genuine, increasing toil

## Proposed Fixes (3 options, ascending complexity)

### Option A: Invoker-level retry (targeted, lowest risk)

Add a retry to `_invoke_job()` for the `dbutils.notebook.run()` call. This catches JVM-level transient errors that bypass the notebook's internal retry:

```python
# In invoker.py
from tenacity import retry, stop_after_attempt, wait_fixed, retry_if_exception_type
from py4j.protocol import Py4JJavaError

@retry(
    stop=stop_after_attempt(2),
    wait=wait_fixed(60),
    retry=retry_if_exception_type(Py4JJavaError),
    reraise=True,
)
def _run_notebook(self, path, timeout, arguments):
    return dbutils.notebook.run(path=path, timeout_seconds=timeout, arguments=arguments)
```

If the retry succeeds, `done` is logged normally and no false failure occurs.

**Pros**: surgical fix, keeps lifecycle logging correct, no changes to DagProcessor or DagTerminator.
**Cons**: only covers pre/post-run invoker failures; other transient errors in `Processor.run()` are not addressed.

### Option B: DagProcessor retry mechanism (robust, higher complexity)

Add retry logic to `DagProcessor.receive()`. Instead of unconditionally setting `Status = "ok"`, re-queue failed items:

```python
# In processor.py receive()
failed = False
try:
    dbutils.notebook.run(...)
except Exception:
    LOGGER.warning("fail", extra={"label": j.get("Job")})
    failed = True
finally:
    retry_count = j.get("RetryCount", 0)
    if failed and retry_count < self.step.max_retries:  # new config
        j["Status"] = "scheduled"
        j["RetryCount"] = retry_count + 1
        azure_table.upsert(j)
        LOGGER.info("retry", extra=self.extra(j))
    else:
        j["Status"] = "ok"
        azure_table.upsert(j)
        LOGGER.info("end", extra=self.extra(j))
        # Only clear dependencies on final completion
        dependencies = azure_table.query(...)
        azure_table.delete(dependencies)
    TABLE_LOG_HANDLER.flush()
```

The `send()` thread picks up re-scheduled items on its next 5s poll cycle. Retries stay within the same `_process()` execution, so `write_logs()` captures all lifecycle entries.

Requires a new `max_retries` config per step (default: 0 for backward compatibility).

**Pros**: covers ALL transient failures (invoker, processor, anything), logs are coherent, configurable per step.
**Cons**: larger change, needs retry predicate to exclude non-transient errors, dependency clearing logic becomes more nuanced.

### Option C: DagTerminator tolerance (reporting safety net)

Make `terminate()` smarter about what constitutes a genuine failure. Instead of just checking for `done`, verify the last outcome and optionally cross-reference Delta:

```python
# In terminator.py terminate()
not_done_df = SPARK.sql("""
    WITH last_outcome AS (
        SELECT job,
               max_by(status, timestamp) AS last_status
        FROM {logs}
        WHERE status IN ('done', 'failed')
        GROUP BY job
    )
    SELECT job FROM last_outcome WHERE last_status = 'failed'
""", logs=logs_df)
```

This checks the **last** outcome per job rather than requiring any `done` to exist. Items that failed then succeeded are not reported.

For additional robustness, a Delta DESCRIBE HISTORY cross-reference could verify that a table received a write after its failure timestamp.

**Pros**: handles cases where retry logs are lost, no change to dispatch/retry path.
**Cons**: DESCRIBE HISTORY is a heuristic (a write could be from a manual run). Adds runtime cost to terminate. Doesn't fix the root cause.

## Recommended Approach

Option A + C together provide the best balance: A fixes the root cause for the common case (transient invoker errors), C acts as a safety net for edge cases where logs are incomplete. Option B is the most robust long-term solution but is a bigger change, worth considering as a follow-up.

## Current Workaround

Two project-level mitigations are in place:

1. **Increased retry window in the pre-run invoker notebook**: 5 attempts with `wait_exponential(multiplier=20, min=30, max=120)` (~10 min total window), reducing the chance of all retries failing.
2. **Delta recovery check in the terminate notebook**: after `terminate()` raises, each candidate failure is verified against `DESCRIBE HISTORY`. If the table received a write after the failure timestamp, the item is treated as recovered and excluded from the failure count.
