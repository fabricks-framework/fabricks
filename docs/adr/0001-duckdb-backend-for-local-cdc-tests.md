# ADR 0001: Local CDC/DDL testing without Databricks

## Status

Proposed — design agreed, not yet implemented. Staged: Stage 1 is the
near-term plan; Stage 2 is documented but deliberately deferred.

## Problem

`Merger`/`Processor`/`Generator`/`Configurator` (CDC layer, `framework/fabricks/cdc/`)
and `Table` (`framework/fabricks/metastore/table.py`) can only be exercised
today via the integration suite, which runs as Databricks notebooks against a
live cluster (see [TEST.md](../TEST.md)). There is no way to test CDC merge
logic or DDL generation without Databricks.

## Decision

Two stages. Stage 1 gets real local CDC/DDL test coverage with the smallest
possible change: a local (non-Databricks-Connect) Spark session running real
Delta, so the exact production SQL runs unmodified. Stage 2 — a second,
non-Spark backend (DuckDB), for test speed — is designed here but **not**
built until Stage 1 has proven the approach is worth it. Stage 1 was chosen
over building Stage 2 first because it deletes the two riskiest, largest
pieces of Stage 2's design (a production merge-template rewrite, and an
Narwhals-based rewrite of `Configurator`'s DataFrame plumbing) entirely,
rather than merely shrinking them — see "Effort comparison" below.

### Scope split: DDL vs. merge SQL (applies to both stages)

- **DDL** (`Table._create`) is snapshot-tested as generated SQL text, not
  executed. It uses Databricks/Unity-Catalog-only features with no non-cluster
  equivalent: identity columns (`generated by default as identity`), liquid
  clustering (`cluster by`), column masks (`mask <name>`), `tblproperties`.
  This applies even under Stage 1's real local Delta — these are Databricks
  Runtime/Unity-Catalog features, not cluster-vs-local features, so plain
  `delta-spark` doesn't have them either.
- **CDC merge SQL** (`Merger.get_merge_query`, the `merges/*.sql.jinja`
  templates) is actually executed, to verify merge correctness
  (scd0/scd1/scd2/nocdc), not just the generated text.

### Bronze ingestion stays out of scope (both stages)

`read_stream`/`_read_stream` uses `spark.readStream.format("cloudFiles")`
(Auto Loader: schema evolution, incremental listing, checkpoints) — genuine
Databricks-only machinery, no local equivalent under either stage. Local
tests exercise `Merger`/`Processor`/`Table` directly with already-derived
rows, not the full Bronze→Silver→Gold pipeline.

---

## Stage 1: local Spark + Delta (`delta-spark`, no Databricks Connect)

The production code runs completely unmodified — no template rewrite, no
`Configurator` rewrite, no backend abstraction. What's new:

1. **Local SparkSession with Delta configured.** `utils/spark.py`'s
   `get_spark()` gains a third branch. The old `DATABRICKS_LOCALMODE` boolean
   only distinguished "local machine via Databricks Connect to a remote
   cluster" from a `false` default that conflated two different things
   (native Databricks cluster, and this plan's fully-local test environment).
   Replaced with `FABRICKS_ENVIRONMENT: Literal["docker", "remote",
   "databricks"]` (`fabricks/utils/environment.py`, a new, deliberately
   Spark-free module — importing from `utils/spark.py` would pull in
   `pyspark`/`databricks.sdk` and eagerly build a session as a side effect,
   violating `utils/path`'s "no Spark dependencies" contract, since Stage 1's
   path dispatch (#2 below) needs the same value). `get_spark()`'s new
   `"docker"` branch builds the Delta-configured session
   (`configure_spark_with_delta_pip`, Delta extensions/catalog config) as
   production code, not a test-only fixture — Stage 1's test fixture
   delegates to it rather than duplicating the builder. Default
   (`"databricks"`) preserves existing behavior for every caller that sets
   nothing; blast radius verified low before replacing outright (3 files in
   the whole repo referenced the old flag).
2. **`FileSharePath` hard-calls `dbutils.fs.*`.** `Table.delta_path`/
   `Database.delta_path` are `FileSharePath`s, and `FileSharePath.exists()`/
   `walk()`/`rm()` (`utils/path/file_share.py`) call `dbutils.fs.*` directly
   — genuinely Databricks-only, no fallback today. Resolved: add a new
   sibling class, `LocalFileSharePath(BasePath)`, alongside the existing
   `FileSharePath`/`GitPath` — not a fallback branch inside `FileSharePath`,
   and not a reuse of `GitPath` (which is 90% of the way there — `exists()`/
   `walk()`/`_yield()` are already plain `pathlib`, no `dbutils` — but has no
   `.rm()`, since only `FileSharePath` defines one, and `Table.drop()`/
   `Database.drop()` need `.rm()` for test teardown; `GitPath`'s existing
   role is read-only access to checked-in repo files, a different concept
   from a mutable local storage root, so overloading it would blur that).
   Only 4 files construct `FileSharePath(...)` directly (`file_share.py`
   itself/`resolve_fileshare_path`, the deprecated `Path` factory,
   `tests/databricks/utils.py`, `utils/read/read.py`), and
   `BasePath.joinpath()`/`.append()`/`.parent()` all build derived paths via
   `self.__class__(path=...)` — so swapping the class only at the root
   (the storage path passed in for tests) propagates through every
   `.joinpath()` call downstream (`Table.delta_path`, etc.) without touching
   those methods. Smaller than Stage 2's backend abstraction, and smaller
   than it first looked. `resolve_fileshare_path()`'s dispatch (which class
   to build) reads `FABRICKS_ENVIRONMENT` (`"docker"` → `LocalFileSharePath`,
   otherwise → `FileSharePath`) rather than sniffing whether the path string
   starts with `abfss://` — an explicit environment check instead of
   inferring intent from path shape, and it can assert the `abfss://` shape
   still holds for the non-`"docker"` case, catching a storage
   misconfiguration loudly instead of silently mis-dispatching on it.
3. **Fixture reuse is more direct than Stage 2's.** `tests/databricks/utils.py`'s
   `convert_json_to_parquet`/`convert_parquet_to_delta` already do this exact
   thing with real Spark and real Delta — they need path/dbutils substitution
   (point at a local temp dir instead of cloud storage; drop the
   `for i in range(1, 4)` Unity-Catalog 3x-replication workaround, which is
   UC-only and irrelevant here) rather than being ported to a different
   engine.
4. **Creating test tables needs nothing new.** Already an existing pattern —
   `deploy/tables.py`'s `create_table_step`/`create_table_log`/
   `create_table_dummy` show it: `Database(name, spark=local_spark).create()`
   is just `spark.sql("create database if not exists ...")`, which works
   against Spark's built-in local embedded Hive metastore
   (`build_spark_session` already calls `.enableHiveSupport()` — no
   catalog/Unity-Catalog setup needed, local or Databricks).
   `Table(database, *levels, spark=local_spark).create(schema=StructType([...]))`
   runs the same `_create()` DDL production uses, for a table with a known
   fixed schema. For the CDC target tables under test (Bronze/Silver/Gold),
   no manual `.create()` call is even needed — `Merger.merge()`/
   `Processor.append()` already auto-create on first use
   (`if not self.table.exists(): self.create_table(src, **kwargs)`) with a
   schema inferred from the first fixture batch's DataFrame, same as
   `create_table_dummy` does with `cdc.overwrite(df)`. The only thing tests
   add on top: point `Database`/`Table` at the `LocalFileSharePath` root (#2
   above) so `location '...'` in the DDL lands in a local temp dir.

   Local tests call the CDC layer directly (`NoCDC`, `SCD1`, `SCD2`,
   constructed as `NoCDC("bronze", "king", "scd1", spark=local_spark)` etc.)
   rather than going through the `Bronze`/`Silver`/`Gold` job classes,
   `get_job()`, or any job-config YAML — matching the pattern
   `tests/databricks/jobs/job1/test_cdc.py` already uses. This isn't just
   about avoiding Bronze's parser/streaming machinery (which direct `NoCDC`
   calls sidestep automatically, since no `Bronze` job object is ever
   constructed) — `Configurator.__init__(database, *levels,
   change_data_capture, spark=None)` only resolves `Database(database)`, a
   storage-path lookup, so no job config is needed for *any* layer
   (bronze/silver/gold), not just bronze. `__key`/`__hash`/`__merge_key`/
   `__merge_condition` are computed internally by
   `Processor.get_query_context()` from a `keys=` kwarg and the src's raw
   columns — never something the caller needs to pre-compute. Combining
   multiple bronze sources (e.g. `king_and_queen`'s two parents) is done by
   the test itself (a plain `DataFrame.unionByName`) before the single
   `SCD1`/`SCD2.update()` call, since that's normally `Silver` job-level
   dependency-lineage logic (`get_dependencies_lineage`/`concat_dfs`), not
   CDC-layer logic — bypassing the job layer means reproducing that one
   step by hand.
5. **Tables are built once per session, not per test.** Not a new pattern —
   the existing Databricks integration suite already works this way
   (`pytest.mark.order` across `job1`..`job5`, ordered phases building tables
   up incrementally, many test functions asserting against the result — see
   `TEST.md`). Reapplied locally: a session-scoped fixture builds the local
   Spark+Delta session and database once, then drives each job's NDJSON
   batches through the real CDC layer in order (`cdc.merge()`/`.overwrite()`/
   `.append()`) — table creation and data loading are the same act, since
   `Merger.merge()` auto-creates on the first batch (#4 above). Individual
   test functions query the already-built tables and assert; nothing is
   recreated per test. A test that needs to check state after a specific
   batch (not just the final state) is an ordered test sharing the session
   table — assert, apply the next batch, assert again — same as the existing
   `job1`..`job5` phase model, not a new mechanism.

   `job1`..`job11` are not independent scenarios — the fixture data itself
   confirms this (`job1/king/2022/01/01`, `job2/king/2022/02/05`,
   `job3/king/2022/03/01`, ... — same entities, successive dates): they're
   the sequential batches of one continuous CDC history. `job3` only has
   something to test because job1's and job2's batches already built and
   populated the table, matching `TEST.md`'s "later jobs depend on tables
   earlier jobs produced." The session fixture already replays every job's
   batches in order, so this is inherent to the design, not a separate thing
   to verify.

   One consequence this surfaces: the Databricks integration suite can get
   away with letting you select a subset (`pytest -k job3`) because it
   relies on **persistent workspace state** across separate pytest/notebook
   invocations — job1/job2 already ran previously and left real Delta tables
   behind. Local tests have no such persistence (each invocation starts a
   fresh, ephemeral local session).

   **Refinement (Stage 1 implementation): the sequential unit is the *job*,
   not the raw landing-file batch, and scenarios are explicit job lists
   rather than an implicit "always replay from job1."** Verified against
   the actual merge templates: `scd2.sql.jinja`'s `__scd2_base` CTE derives
   `__valid_from`/`__valid_to` via `lead(__timestamp) over (partition by
   __key order by __timestamp)`, which already historizes every same-key row
   correctly *within one `.update()` call*, regardless of how many raw
   `YYYY/MM/DD/NNNN` batch files contributed those rows — job1's 2 king
   batches and 3 queen batches all merge correctly in a single call. So the
   raw-batch boundary inside a job doesn't need sequential calls (and
   splitting per raw-batch would be wrong: `correct_valid_from`'s
   epoch-start rewrite is a global minimum over the whole call's result set,
   and reapplying it per batch would misstamp each batch's own earliest row).
   What *does* need sequencing is the **job** boundary — each job's
   `.update()` call should run against whatever table state the *previous
   job's* call left behind, since that's what exercises the
   incremental-merge-into-an-already-populated-table code path
   (`Processor.get_query_context()`'s `has_rows` branch) that a single-job
   scenario never touches.

   Rather than one implicit rule ("always replay job1 through the highest
   job number"), each test scenario is an explicit, named job list (e.g.
   `[1]`, `[1, 2]`, or `[2, 3]` — skipping job1 entirely is a valid,
   different starting point, not just a truncated replay) that builds its
   own isolated tables from empty, topic-suffixed by the job-list signature
   so multiple scenarios coexist in one session without sharing state. This
   is a more general solution to the same problem the "unconditional replay"
   rule above was solving (no dependence on leftover state or execution
   order between local runs) — `pytest -k` selecting a subset of scenarios
   still sees each selected scenario build its own correct, self-contained
   state, rather than needing every job up to some number to have run first.

   **Actual Stage 1 scope: every contiguous prefix `[1]` through `[1..9]`**
   (9 scenarios) — verified as the full range where both `king` and `queen`
   have plain, non-deletelog raw data (`job10` has `queen__deletelog` only,
   `job11` has no queen folder at all). Chains beyond `[1]` merge job2+'s
   data — which introduces a new column (`newField`, verified present
   through job9) — into a table whose schema was created from an earlier
   job; since this design bypasses job orchestration's own `update_schema()`
   calls entirely, this needed Delta's `spark.databricks.delta.schema.
   autoMerge.enabled` enabled on the local session (confirmed a core OSS
   Delta Lake feature, not Databricks-Runtime-only, despite the
   `spark.databricks.*` config namespace — available since Delta 0.6.0),
   matching what production's `add_spark_options_to_spark()` already sets
   for every real Databricks session rather than inventing local-only
   schema-reconciliation logic. Scenarios that skip job1 (e.g. `[2, 3]`) are
   not populated — job2 alone was never verified as independently mergeable
   into an empty table, unlike job1 which establishes the base schema every
   later job's drift builds on.
6. **Pre-derived fixtures, generated once and git-committed.** Run the
   derivation once via a script, commit the output, don't re-derive per test
   run — same rationale as originally designed for Stage 2 (see below).
   Format: **NDJSON** (git-diffable, and represents the `__metadata` struct as
   a nested object directly rather than flattening/stringifying it as CSV
   would need to). Since Stage 1 loads fixtures through real Spark, NDJSON's
   lack of native typing is less of a cost than under Stage 2 — Spark can be
   given an explicit schema on read, no separate type-mapping table needed.
7. **Assertions reuse the existing `expected/**/job*.sql` mechanism, not
   ad-hoc per-test checks.** Correction to how this repo's existing golden
   files actually work: `tests/expected/{silver,gold}/{scd0,scd1,
   scd2}/job*.sql` (a top-level sibling of `tests/unit/`/`tests/local/`/
   `tests/databricks/`, not nested under `tests/databricks/` — both
   `tests/databricks/` and `tests/local/` consume it, so it isn't owned by
   either) are not SQL-text snapshots diffed as text — they're
   reference *queries*, materialized into views by `create_expected_views()`
   (except each job's `silver/scd2/jobNN.sql` — the root of the per-job DAG,
   a literal `create ... from values (...)` list, i.e. genuinely hardcoded
   data rather than a query. `job01.sql` is converted to `job01.ndjson`
   during the `data`/`expected` extraction, named-field rows instead of
   positional `col1, col2, ...` tuples matched against a separate `cast(colN
   as type) as name` header; `create_expected_views()` loads it with an
   explicit schema and registers it as a real table so every other file's
   `from expected.silver_scd2_job{N}` reference keeps working unchanged.
   Only job1 is converted — job02-job11 stay as `.sql`, and not because
   they're out of scope: read directly, `job02.sql`/`job03.sql` are each
   `VALUES (...) union all select ... from expected.silver_scd2_job{N-1}
   where not __is_current` — a genuine sequential chain of hand-authored
   rows referencing the *previous* job's view, not a standalone data root
   the way job1's is. `create_expected_views()` must still run these `.sql`
   files, in ascending order, for job2-9's scenarios to have anything to
   compare against — an early `return` after the NDJSON branch (present in
   an earlier draft of this design) would have silently skipped creating
   `expected.silver_scd2_job{2..9}` entirely; fixed to fall through to the
   `.sql` loop instead.)
   (`tests/databricks/utils.py`, plain `spark.sql(GitPath(v).get_sql())`)
   as `expected.silver_{cdc}_job{iter}`/`expected.gold_{cdc}_job{iter}`, and
   compared against the actual job table's *data* via
   `compare_silver_to_expected`/`compare_gold_to_expected` →
   `assert_dfs_equal` (`tests/databricks/compare.py`) — a full
   `pandas.testing.assert_frame_equal` after normalizing decimals/
   timestamps/booleans/nulls (`decimal_to_double`/`timestamp_as_string`/
   `boolean_as_string`/`value_to_none`, `utils/dataframe.py` — plain
   PySpark `.select()`/`.cast()`, no Databricks dependency). This whole
   chain is Spark-native and fully portable: Stage 1 reuses the existing
   `expected/**/job*.sql` files and `compare.py`'s comparison functions
   almost verbatim, rather than writing new ad-hoc assertions per test.
8. **Materialized per-checkpoint table snapshots enable parallel test
   execution.** The session-scoped fixture (#5) forces every test onto one
   shared, sequentially-built session — fine for correctness, but it means
   tests can't run in parallel across job scenarios (job5's tests can't
   start until job1..job4's batches have been replayed in the same session).
   Decouple the two: also materialize the *post-CDC* table state after each
   job checkpoint (state after job1's batches, after job1+job2's, ...), not
   just the raw pre-CDC NDJSON input batches (#6). Each job's test suite then
   loads its own checkpoint snapshot directly and runs independently — no
   shared live session, no serialization, safe to run in parallel (e.g. under
   `pytest-xdist`).

   Format: **Parquet**, unlike the raw NDJSON fixtures. These are derived
   cache artifacts, not hand-authored input — exact type round-trip and fast
   loading matter more here than PR-diff readability, and correctness is
   validated by the slow mode below, not by reading a diff.

   Risk: a cached checkpoint snapshot that's never regenerated silently goes
   stale — tests pass against output the *current* merge logic would no
   longer actually produce, same drift risk already flagged for the raw
   fixtures and the (Stage 2) type-mapping table. This requires two modes,
   not one: a **slow, sequential mode** that replays every batch live through
   the real CDC layer from the raw NDJSON (#5's session fixture) — this is
   what *generates* the checkpoint snapshots, and must run at least in CI to
   catch drift — and a **fast, parallel mode** that just loads the
   already-built checkpoint snapshots and asserts, used for everyday local
   iteration. The fast mode can't validate itself; only the slow mode proves
   the snapshots are still correct.

### Effort comparison vs. building Stage 2 (DuckDB) first

Going local-Spark+Delta-first eliminates, not just shrinks:

- The merge template rewrite (struct dot-path assignment works natively in
  real Spark/Delta — only a problem for DuckDB's `MERGE`).
- Narwhals adoption and the `Configurator.get_src`/`get_columns`/
  `reorder_dataframe`/`has_data` rewrite (real PySpark `DataFrame`s work
  as-is).
- The backend Strategy abstraction (`DeltaBackend`/`DuckDBBackend`) — with
  only one engine, there's nothing to inject.
- The Spark→DuckDB type-mapping table and its own test coverage.
- Trusting `sqlglot`'s Databricks→DuckDB transpile across every construct in
  `scd0/scd1/scd2/nocdc` — unverified risk, gone.

Rough magnitude: Stage 1 is roughly a third to half the work of building the
DuckDB backend first, because it deletes the two largest, riskiest line items
outright rather than trimming them. What it doesn't get you: it's slower
per-test (JVM startup, real Spark) — the reason DuckDB was considered in the
first place. That trade-off is deferred to Stage 2, not resolved.

## Stage 2 (deferred): DuckDB as a second backend

Kept as a documented plan, not built until Stage 1 shows the approach earns
its keep and test speed becomes an actual felt problem.

- **Backend architecture.** Two backends: Delta/Databricks (Stage 1) and
  DuckDB. A third backend (Postgres/Lakebase, see the Lakebase migration
  plan) is a possible future addition — the interface is scoped to what these
  two need, not designed for a third in advance. Structured as an **injected
  backend object** (Strategy pattern): `Table`, `Merger`, `Generator`,
  `Processor`, `Configurator` stay single classes; a `backend` object
  (`DeltaBackend` / `DuckDBBackend`) is injected and handles engine
  differences. Not parallel class hierarchies — avoids doubling the class
  count and the two hierarchies drifting apart.
- **`Table`'s backend interface** covers only what the CDC/DDL-creation path
  touches: `create`, `exists`/`registered`, `rows`, `columns`,
  `get_schema_differences`. The rest of `Table` (`vacuum`, `optimize`
  /zorder/vorder, `create_bloomfilter_index`, `restore_to_version`,
  `enable_liquid_clustering`, comment management, `describe_history`, etc.)
  stays Delta/Databricks-only; calling it under the DuckDB backend raises
  `NotImplementedError`.
- **DataFrame layer: Narwhals.** `Configurator.get_src`/`get_columns`/
  `reorder_dataframe`/`has_data` call PySpark `DataFrame` methods directly
  (`.columns`, `.dtypes`, `.select()`, `.isEmpty()`,
  `df.schema[name].jsonValue()`), not just `.sql()`. Rewritten against
  [Narwhals](https://github.com/narwhals-dev/narwhals)'s lazy-frame API,
  which supports both PySpark and DuckDB. Production wraps a real PySpark
  `DataFrame`; the DuckDB backend wraps a DuckDB relation. Narwhals doesn't
  cover global-temp-view registration (a Spark-catalog side effect) — see
  below.
- **Merge template rewrite: struct field updates.** `merges/*.sql.jinja`
  updates `__metadata` (`struct<file_path, file_name, file_size,
  file_modification_time, inserted, updated>`, see `Silver.update_metadata`)
  by dot-path assignment: `__metadata.updated = cast(current_timestamp() as
  timestamp)`. DuckDB's `MERGE` can't assign into a struct field this way.
  Rewrite to rebuild the whole struct (`__metadata = struct_pack(...)` or
  equivalent) — one template, works on both backends, no per-backend
  variant. `sqlglot`'s existing `Fabricks(Databricks)` dialect
  (`utils/sqlglot.py`) is expected to handle the rest of the transpile
  (`<=>` → `IS NOT DISTINCT FROM`, `array_join`/`array()`/`md5()`/
  `interval 1 seconds`, etc.) — unverified until implemented.
- **Global temp view → materialized view.**
  `create_or_replace_global_temp_view` (`metastore/view.py`) renamed to
  `create_or_replace_materialized_view`, backend-dispatched: Spark backend
  unchanged (`df.createOrReplaceGlobalTempView`, returns `global_temp.<name>`);
  DuckDB backend `CREATE OR REPLACE TABLE <name> AS SELECT ...`, returns
  `<name>`. `CREATE OR REPLACE TABLE` mirrors Spark's overwrite-on-every-call
  semantics, so no separate drop step is needed.
- **Type mapping (Spark → DuckDB).** DuckDB fixture tables are built from the
  *same* `StructType`/`dtypes` already used to generate production DDL — one
  Spark-type → DuckDB-type mapping table (string → VARCHAR, long → BIGINT,
  decimal(p,s) → DECIMAL(p,s), timestamp → TIMESTAMP, struct → STRUCT(...),
  etc.), reused everywhere a DuckDB table needs creating from a Spark schema,
  rather than each test hand-authoring DuckDB DDL. Needs its own test
  coverage — a silent gap for an untested Spark type produces a
  wrong-but-running merge, not a loud failure. Timestamp semantics
  (`TIMESTAMP` vs. `TIMESTAMPTZ`, matching `spark.sql.session.timeZone` and
  SCD2's `__valid_from - interval 1 seconds` arithmetic) not yet resolved.
- **Fixture data** reuses the same NDJSON files Stage 1 already produces —
  Stage 2 reloads them through the type-mapping table into DuckDB instead of
  through a Spark schema.

## Rejected alternatives

- **Full Table interface parity** (Stage 2): DuckDB implementing all ~40
  `Table` methods (including Delta-only maintenance operations) was rejected
  as fabricating behavior with no real DuckDB analog.
- **Generalizing the backend interface for a 3rd (Postgres/Lakebase) backend
  now**: rejected — design for what Delta and DuckDB need; revisit if and
  when the Lakebase migration actually starts.
- **New, independent fixtures instead of reusing `tests/data/**`**:
  rejected — reusing the same king/queen/prince scenarios keeps results
  comparable to the Databricks integration suite's known-good output, and the
  derivation logic already exists (`tests/databricks/utils.py`).
- **Leaving `data/`/`expected/` nested under `tests/databricks/`**: rejected
  — `tests/local/` also consumes both, and reaching into a directory named
  for a different suite is a worse coupling than the one-time cost of
  hoisting them to top-level `tests/data/`/`tests/expected/` siblings.

## Open / not yet decided

- Stage 1: resolved — fixture generation and the new suite live in
  `tests/local/` (with a small carve-out: fixture-generation's own test
  lives in `tests/unit/` instead, since it has no Spark dependency and
  `tests/local/`'s `conftest.py` would otherwise force a JVM/Docker cost on
  it just by directory-scoped collection). CI wiring remains explicitly out
  of scope.
- Stage 1: job10/job11 — genuinely out of scope, not deferred: `queen` has
  no plain (non-deletelog) data past job9. Extending needs real design work
  (delete-log handling or an entity-optional merge path), not a data-only
  extension.
- Stage 1: scenarios that skip job1 (e.g. `[2, 3]`) — the job-sequential
  mechanism supports this, but no such scenario is populated; job2's raw
  data was never verified as independently mergeable into an empty table.
- Stage 1: type-changing schema drift (as opposed to a new column) between
  job1 and job9 — `autoMerge` is confirmed to handle job2's new `newField`
  column, but a genuine column type change (not verified absent across
  job3-job9's raw data) would need `update_schema(widen_types=True)`-style
  handling `autoMerge` alone doesn't provide.
- Stage 2: exact Spark→DuckDB type-mapping table contents and its own test
  coverage; TIMESTAMP vs. TIMESTAMPTZ handling; whether `sqlglot`'s
  Databricks→DuckDB transpile is actually sufficient for every construct in
  `merges/*.sql.jinja` beyond the struct-update fix.
- When (or whether) Stage 2 gets built at all — deferred until Stage 1's test
  speed is an actual felt problem, not assumed in advance.
